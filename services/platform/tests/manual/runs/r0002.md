## Scope

and TOTP login, consent allow/cancel/retry, and keyboard access at a narrow
viewport. It also opened a synchronized API-only Inbox thread, sent a text
reply, acknowledged it through the native source domain, and reloaded the page.

a feature-focused round, not a fresh full-catalogue baseline on an untouched
tree. Browser page errors were captured throughout; none occurred in the
successful repeat passes. The separate native integration harness covers fresh

### R2-1 · Duplicate callback navigation

**Surface** Native consent and continuation · **Repro** Allow the registered
test client, then repeat sign-in · **Expected vs actual** One verified callback
was expected; two browser navigations raced the same one-use callback.

Better Auth's default browser fetch plugin already handles its redirect
response. The component additionally assigned the returned URL, which raced
the callback's code exchange. The component now leaves redirect ownership with
the maintained plugin.

**Fix** `oauth-authorization.tsx` · **Pinned by**
`oauth-authorization.test.tsx` (consent decisions, StrictMode, redirect ownership
and accessibility) and a repeated real browser allow/cancel/retry pass.

## Not reached

Hardware passkey and an external SSO provider continuation were not driven in
this isolated fixture. The production relying-party callback through the
private overlay and source-app attachment rendering belong to the deployment
round. Existing authentication and conversation catalogue boxes outside this
targeted scope were not rerun manually.

## Verdict

The duplicate navigation was fixed and the browser sequence was repeated
successfully. Desktop and narrow consent layouts, TOTP continuation and a
persisted API reply were observed. Protocol refusal, concurrency, attachment
and replay checks are recorded in the automated integration lane; this round
does not claim a full manual catalogue pass.
