# Workflows — Manual Test Plan

> **Purpose**: Exercise workflow detail pages — the flow editor (canvas +
> Editor / Executions / Configuration / Triggers sub-tabs, the **History**
> dropdown-menu button in the tab strip's action slot
> (`workflows.navigation.history`) — not a routed sub-tab — and the AI
> Assistant panel), the in-editor tester, and webhook / schedule / event
> triggers firing into the executions list. The old standalone workflow surface
> (list / catalog / metrics tabs and the create-workflow flow) was removed —
> workflow detail pages are reached by direct link (automations' workflow
> blocks link here). An unresolved `/automations/{slug}` renders the
> automation not-found state; there are no legacy redirects. Mock-LLM mode A
> is sufficient (the seeded `test` workflow runs offline).

## Scope & routes

| Surface         | Route                                                                     |
| --------------- | ------------------------------------------------------------------------- |
| Editor (canvas) | `/dashboard/{org}/workflows/{slug}`                                       |
| Editor sub-tabs | `/dashboard/{org}/workflows/{slug}/{configuration\|triggers\|executions}` |

`{slug}` is the workflow slug (e.g. `test`); the dynamic route file is
`$workflowId` but the URL segment carries the slug (`$workflowId.tsx` runs
`urlParamToSlug(workflowId)`). The Editor canvas is the index of `$workflowId`
(no `/editor` segment in the URL). There is no standalone workflows list —
`/dashboard/{org}/automations` is Automations itself now (see
[automations.md](automations.md)). A `/automations/{slug}` whose slug names no
installed or catalog automation renders the hub's **Automation not found**
empty state — no redirect, cold or warm.

## Prerequisites

Bring the stack up and sign in per [SETUP.md](SETUP.md). Mode A seeds each new
org's filesystem config with a trivial `test` workflow (`workflows/test.json`,
a single `start` step) that is runnable end-to-end offline.

> **Agent note**: a chat-style tester turn / execution reaches its terminal
> state when the result badge shows **Completed** (`workflows.tester.result.completed`)
> or **Execution failed** (`workflows.tester.result.failed`) — wait on that
> badge, not on text. The e2e suite budgets ~90 s for a real seeded run. On-canvas
> step editing isn't wired up yet, so the canvas is read-only: the add-step **+**
> button is disabled and node handles / edges can't be edited.
